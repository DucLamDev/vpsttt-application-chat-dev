# WebTui Chat Desktop

Tauri host for the WebTui Chat desktop application.

This app does not contain a second React UI. Development loads the Next.js web
dev server from `apps/web`; production bundles the static export generated by
`npm --workspace @webtui/web run build:desktop`.

## Commands

From `frontend`:

```bash
npm run dev:desktop
npm run build:desktop
npm --workspace @webtui/desktop run build:release
npm --workspace @webtui/desktop run write-updater-manifest
```

The Tauri CLI must be available in the environment. The Rust host is intentionally
thin: native capabilities live behind `@webtui/chat-core` platform contracts so
web and desktop can share feature code.

## Voice and Video Calls

The desktop app uses the same WebRTC call UI and signaling flow as the web app.
Tauri only needs to allow media capture and WebRTC traffic in CSP, then the
system webview prompts for camera/microphone access.

- macOS permission descriptions live in `src-tauri/Info.plist`.
- Production call pages must run over HTTPS/WSS so browsers and webviews allow
  `getUserMedia`.
- The current peer connection uses a public STUN server. Add a TURN server
  before production rollout for users behind strict NAT, VPN, or corporate
  firewalls.

## Release Packaging

`build:release` creates a temporary Tauri config under
`src-tauri/.generated/` and refuses to continue unless the updater signing
inputs are present:

- `WEBTUI_RELEASE_CHANNEL=stable|beta`
- `WEBTUI_TAURI_UPDATER_PUBKEY`
- `TAURI_SIGNING_PRIVATE_KEY` or `TAURI_SIGNING_PRIVATE_KEY_PATH`

Optional release inputs:

- `WEBTUI_TAURI_BUNDLES=msi,nsis` on Windows, `dmg` on macOS,
  `appimage,deb` on Linux.
- `WEBTUI_TAURI_TARGET` to override the native target triple; macOS defaults to
  `universal-apple-darwin`.
- `WEBTUI_UPDATER_ENDPOINT` to override the default signed updater manifest
  endpoint.
- `WEBTUI_WINDOWS_CERT_THUMBPRINT` and `WEBTUI_WINDOWS_TIMESTAMP_URL` for
  Windows code signing.

After the signed updater artifact is uploaded, generate the manifest served by
the backend updater endpoint:

```bash
WEBTUI_DESKTOP_MANIFEST_DIR=/var/lib/webtui/desktop-releases \
WEBTUI_RELEASE_CHANNEL=stable \
WEBTUI_TAURI_TARGET=windows-x86_64 \
WEBTUI_TAURI_ARCH=x86_64 \
WEBTUI_DESKTOP_VERSION=0.2.0 \
WEBTUI_RELEASE_ARTIFACT_URL=https://downloads.vpsttt.com/webtui-chat/0.2.0/WebTui-Chat.msi \
WEBTUI_RELEASE_SIGNATURE=... \
npm --workspace @webtui/desktop run write-updater-manifest
```

Point the backend at that directory with `DESKTOP_RELEASE_MANIFEST_DIR`. The
default release endpoint is
`/desktop/releases/{channel}/{target}/{arch}/{current_version}`.

Generate updater keys with:

```bash
npm --workspace @webtui/desktop run tauri -- signer generate --ci
```

Only commit the public key through release configuration. Store the private key
in the CI secret store or an offline signing vault.

## Rollback

Keep at least the last stable signed installer and updater manifest available.
If a rollout fails, republish the previous manifest for the affected channel,
raise `DESKTOP_RECOMMENDED_VERSION` only after validation, and never lower
`DESKTOP_MIN_VERSION` below a backend-incompatible client.

## Offline and Network Smoke

Use this checklist before packaging a desktop build:

- Start online, open a busy channel, then turn the network off. The channel list
  and most recent timeline should remain visible with the offline banner.
- Send a text message while offline. It should stay in the local outbox and
  appear as a pending local message after app restart.
- Restore the network. The outbox should retry with the same
  `client_message_id`; the server must return one persisted message, not
  duplicates.
- Test behind corporate proxy/VPN when available. REST calls should update the
  API status pill and WebSocket reconnect should update the realtime status.
- For captive portals or blocked WSS, verify the app shows cached read mode
  instead of logging the user out.
